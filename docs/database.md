# Database (SQLite)

One file, `/data/irtrack.db` in Docker. The schema is defined in `server/schema.ts`: each table matches a type in `src/domain/types.ts`. Column names are the snake_case form of the TypeScript fields (`processId` → `process_id`).

Column types: text, integer, boolean (stored as 0/1), JSON (text holding an array or object that belongs to the row). Child tables have a `position` column for ordering and are deleted with their parent (`ON DELETE CASCADE`).

## First start

A new database is empty: only the tables exist. Settings fall back to defaults in code until a section is saved.

Until the first setup is completed (`meta.setup_completed_at`), every page redirects to `/setup`. There you choose: set up your own organization step by step, or **load demo data** — the complete fictional "Northshore Municipality" set from `server/demo.ts` (contacts, roles, processes, guidance, ~2,500 past incidents, 7 live scenarios), which skips the wizard. The wizard walks through: organization → master data → contacts → roles → reporting obligations → processes → guidance → sources → review. Each step offers templates from `server/templates.ts`, and every step can be skipped.

### Templates

| Kind               | Catalog                                                                                                             | Added automatically with it                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Contacts           | 32 contact types (service desk, SOC, privacy officer, suppliers, regulators …) without phone numbers; 112 included  | —                                                                                      |
| Roles              | 12 roles with responsibilities and decisions                                                                        | —                                                                                      |
| Reporting rules    | GDPR art. 33, Cbw/NIS2, sector exception profile                                                                    | —                                                                                      |
| Processes          | 9 processes (IT, security, privacy, facilities, safety, HR, continuity, IRT, CRT)                                   | the roles and reporting rules they use, plus RACI                                      |
| Guidance           | 12 situations with first steps and flowcharts                                                                       | their process and roles                                                                |
| Sources            | TOPdesk, ServiceNow, Jira SM, CSV, webhook (field and value mappings)                                               | —                                                                                      |
| Incident playbooks | 8 playbooks (ransomware, phishing, misdirected data, water damage, accident, integrity, supplier outage, IT outage) | not stored: tasks, draft messages and improvement actions are copied into the incident |

Template ids become entity ids (`p-security`, `r-privacy`, `c-2`). References to items that are not in the database are dropped; when the missing item is added later, links are restored (for example a role's contacts or a process's reporting rules).

## Schema changes

The schema version is stored in `PRAGMA user_version`. To change the schema, raise `SCHEMA_VERSION` in `server/db.ts` and add a migration step (for example `ALTER TABLE … ADD COLUMN …`) next to the field in `server/schema.ts`. Existing databases are migrated on start.
